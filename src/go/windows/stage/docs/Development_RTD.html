3. Real Time Device Development

This chapter contains practical information for developers of applications (firmware) for Real Time Devices.

3.1. Identifying Devices

In the sections below, we refer to Real Time Devices by OS Serial Number. There are multiple ways to retrieve that from other identifiers.

3.1.1. From Device Name

If the Device Name is given, just run:

$ m2cp device info <the device name>
...
OS Serial: ...

Sometimes device names contain the Hardware Serial Number, but this is a convention that is not required.

3.1.2. From Hardware Serial Number

If the Hardware Serial Number is given, you can search for the Asset that represents this device:

$ m2cp asset find <the hardware serial>
...
  Device OS Serial: <the OS serial number>

The find command may return multiple assets. Look for the one of type “Real Time Device” with the matching Hardware Serial Number. If it has a “Device OS Serial” entry, this the OS Serial Number we are looking for. If the “Device OS Serial” entry is missing, then the asset for the Real Time Device is not properly configured!

3.1.3. From Hardware Assembly Number

If the Real Time Device is hidden in its housing, the Assembly Number must be readable on the housing. The assembly number should be linked to an asset, so we can search for it:

$ m2cp asset find <the assembly number>
...

The OS Serial Number is then to be retrieved from the assembly’s child assets.

3.1.4. By Device Type

As a last resort, list all devices and filter by type for Real-time Devices only:

$ m2cp device list --type rtd
Serial
<the OS serial> ...

Note

Before CLI version 1.8.0 you can had to filter by CPU architecture. Only Real-time Devices have the value arm32:

$ m2cp device list --arch arm32
Serial
<the OS serial> ...

The listing will contain the OS Serial of your device. But if the device info metadata does not give you any hint, then you can’t identify your device.

3.2. Creating Device Models

Device Models are created implicitly by the App Store. There is currently no manual process to create them. A new Device Model is automatically created when:

  • Firmware Upload: When uploading firmware with a device-model value in meta/firmware.yaml that doesn’t exist yet, the App Store creates the Device Model automatically.

  • Firmware Refresh: When a device with an unknown model name is reported during a firmware refresh, the model is created on-the-fly.

In both cases, the App Store also creates an initial Device Model Revision. The architecture is determined either by the architecture field when a new firmware is uploaded, or by information reported during firmware refresh.

3.3. Uploading Firmware

The App Store has a generalized concept of Devices and Apps. The firmware of a Real Time Device is seen as the App running on the Device. That’s why in the following we’ll be talking of deploying firmware as an App.

To deploy firmware to RTDs, a developer must first create a firmware package as a correctly formatted uncompressed tar file:

fw0.bin
fw1.bin
meta/firmware.yaml

The files fw0.bin and fw1.bin are the actual firmware. The file meta/firmware.yaml contains meta information:

app-name: <string>     # App name for this firmware
app-summary: The power board controls the power supply
app-version: <semver>  # Semver version of this upload
device-model: <string> # Device Model Name that this App is built for
offset:
  0: <uint>            # Byte offset for slot 0 
  1: <uint>            # Byte offset for slot 1

# optional fields for expert developers
vendor-id: <string>    # default: generate from store owner details
class-id: <uuid>       # default: generate from vendor-id und device-model
architecture: <string> # default: arm32
bootable: <bool>       # default: false

When a developer uploads a firmware tar with an App name not yet known to the App Store Service, the App Store will create a new App with that name and consider the upload to be its first App Revision. The fields name, architecture and summary are used to create the App Declaration.

All consequently uploaded App Revisions for this App Declaration must have the same values for name and architecture to be accepted.

To upload the packaged firmware use the M2CP CLI

$ m2cp store app push <tarfile> "<upload message>"

# Optionally you can directly rate the app and set a description, which makes it available for installation 
$ m2cp store app push <tarfile> "<upload message>" --description "<proper description of this revision>" --rating "<deprecated|broken|experimental|edge|stable>"

After uploading the new App Revision (i.e. your firmware) you can deploy it to your RTD with the generic tools managing Devices.

3.4. Assigning Firmware to Real-time Devices

After the firmware (or “app”) is available in the store, three steps need to happen to make the app run on one or more devices:

  1. First, a deployment group for the device must exist.

  2. Second, the app must be added to the deployment group.

  3. Third, the device must be within that deployment group.

Only then the app will be installed automatically, once the device is ready for updates. The steps are described in detail in the following.

3.4.1. Creating a new Deployment Group for a Real-time Device

To create a new deployment group for a given device, the Device Model Name and Device Model Revision must be known.

With the OS Serial Number given, you can look at the device info and retrieve its model name and revision:

$ m2cp device info <the OS serial>
...
Model Name:     <the model name>
Model Revision: <the model revision>

Now you are able to create a matching deployment group:

$ m2cp store dgroup create <the dgroup name> rtd <the model name> <the model revision>

In the following, we will refer to that deployment group by name <the dgroup name> for legibility. But generally we recommend to refer to it by ID, which is immutable.

3.4.2. Adding the app to the deployment group

To add the application to the deployment group, we need to know the application’s name and revision in advance. You man look that up by:

$ m2cp store app list --arch arm32
... <the app name>
$ m2cp store app info <the app name> arm32
...
App Revisions
<the app revision>

Now you can add the application to the deployment group named <the dgroup name>:

$ m2cp store dgroup app add <the dgroup name> <the app name> <the app revision>

3.4.3. Adding the device to the deployment group

You set the deployment group of a given device by:

$ m2cp device dgroup set <the OS serial> <the dgroup name>

Note, the device’ model name and model revision must match the deployment group’s model name and model revision!

3.5. Monitoring Firmware Deployment

To observe the current state of firmware deployment to RTDs, use the command m2cp store dgroup info giving the RTDs deployment group as parameter:

$ m2cp store dgroup info <deployment-group>

This shows the currently targeted App (Firmware) version for the deployment group lists its Devices with information on:

  • Pending update actions

  • Last uptime

Then, a new App Revision can be set and a refresh is triggered automatically (wip). You can also trigger the refresh for each RTD individually, using the command:

$ m2cp device refresh <..>

Now the Apps (Firmware) will be deployed to the RTDs. However, only when an RTD reboots, the process is complete. While still on the old partition m2cp store dgroup info will show a pending update for the Device. The decision when to reboot lies with the RTD, implementations differ with use cases To reboot RTDs manually one can use:

$ m2cp device reboot

To get an insight on the success of the update, without waiting for the next reboot, one can view the last result of the update attempt from the ED to the RTD using one of the following methods:

  • device history <OS Serial> --changes shows the update attempts and their results, this is the most user-friendly way (but wip).

  • Execute command m2cp device peers (or listKnownPeers RPC) on the ED the RTD is connected to. The last update result is shown in the fields Last Update Result of the respective RTD. If the result is a success, the update was successful and the RTD will eventually reboot to the new firmware. If the result is an error, the update most likely failed. However, there are some scenarios where the result shows an error or nothing, but the update was successful. See Debugging Problem Scenarios for details.

3.5.1. Debugging Problem Scenarios

Successive Firmware App refreshes

If after a successful refresh, another one is triggered and the respective RTD didn’t reboot inbetween, m2cp-coap will deliver the firmware to the RTD again. As the RTD already received it, it will reply with an error. As the first update was successful, the RTD will eventually reboot and show the new version. So the update is generally successful, but the Last Update Result value will be set to an error. The error code will be -5: Sequence number less or equal to current sequence number. One can trigger a reboot manually to verify it was this issue that caused this behaviour.

RTD does not receive an update from the App Store

Because of a misunderstanding, it can happen, that an RTD does not receive an update from the App Store. To verify this is happening, one can use the RPC command getLastRefreshCall on the ED the RTD is connected to:

$ m2cp device node rpc <node> -c getLastRefreshCall

Note

To find out the correct ED use the command:

$ m2cp device info <RTD>

The field Last Seen Edge Device shows the ED the RTD was last seen on.

This shows the last refresh call made by the ED to the App Store, including the response from the App Store (see Refresh Call). If the response does not contain an update action for the RTD in question, the RTD was most likely not correctly assigned to the deployment group.

A cause for confusion can be, that the same physical RTD can appear as two different RTDs in the list of Known Devices of an ED. Once as legacy RTD and once as modern RTD.

Note

This is because an RTD interacting with the m2cp-coap server using legacy endpoints will be reported with a different OS Serial than one interacting using modern endpoints. So it will cause two Devices to appear in the list of Known Devices, even though they are the same physical device. This is because the legacy endpoints don’t report enough information to conform to the new standards. There are two situations in which this can occur:

  • The RTD changed its Firmware App to a version that supports the modern endpoints. m2cp-coap will retain the information about the legacy RTD for a while.

  • The RTD supports both legacy and modern endpoints. In this case, m2cp-coap will receive information from both endpoints and thus create two different RTDs in the list of Known Devices.

However only one of the two RTDs will be reported to the App Store during the refresh call.

  • If the last seen timestamps of the two RTDs are at least five minutes apart, the older one is filtered out from the list of Known Devices.

  • If the last seen timestamps of the two RTDs are less than five minutes apart, the legacy one is filtered out from the list of Known Devices.

So if the legacy one is the only one that is assigned to a deployment group, the Device will not receive updates. To debug this, use the --unfiltered option of the m2cp device peers command to view all Known Devices, including the filtered out ones to compare it with the output of the RPC getLastRefreshCall.

$ m2cp device peers --unfiltered <ED>
...

$ m2cp device node rpc <node> -c getLastRefreshCall
...

Issues with the Firmware Apps or Manifest.

Here are some known issues that can cause the update to fail, even though the RTD received the firmware:

  • Wrong offset: The offset specified in the meta/firmware.yaml file is wrong. This can only be clarified when looking in the RTDs logs and triggering a refresh.

  • Missing keys: The firmware is missing a required key to verify the firmware. The known keys are persisted in the Known RTDs list of the ED and can be viewed using the listKnownPeers RPC command. However, legacy firmware does not report keys.

  • Update Result is sent to the wrong endpoint: This is an issue that is present in some older firmware versions. The RTD sends the update result to the legacy endpoint instead of the modern one. This doesn’t change the outcome of the update but makes it harder to observe. There are two ways to find out this is happening. Inb both cases the result information can be used from the legacy endpoint:

  • Get the full list of Known Devices using m2cp device peers --unfiltered and check if both a legacy and a modern variant of the RTD are present. If so, check the Last Update Result of both. If the legacy one shows a success and the modern nothing, this is most likely the issue.

  • Advanced: Inspect the logs of the m2cp-coap server (see below) during a refresh request. Look out for update results being sent to the legacy endpoint after the update was announced to the modern endpoint. The logs can be hard to read, so ask for assistance if needed.

Further investigation

Observe the logs of the m2cp-coap server

SSH into the ED:

$ m2cp device ssh open <ED>

Show the logs of the m2cp-coap server:

sudo dev-m2cpctl.m2cpctl logs m2cp-coap -f -m "coap://fw/*" -m "coap://suit/*" -m "coap://hello/*" -m "fw-refresh*"

Trigger a refresh of the RTD:

$ m2cp device refresh <RTD>

From m2cp-coap 6.1.0 onwards, the log level can be modified using the RPC “setLogLevel”. This allows you to increase the log level to “debug” to see more detailed logs.

requires attaching to the RTD via a serial console. Differs from device to device.

3.6. Legacy

3.6.1. Uploading Firmware

The embedded IoT devices built by ML!PA typically run on Riot-OS. As administrators typically don’t have direct access to a peripheral device (e.g. a sensor board), firmware updates use the M2CP-Device as an intermediary. Firmware is deployed to the M2CP-Device via the appstore and then offered to the peripheral devices. Successful installations are reported back to the appstore.

Multiple firmware files for multiple peripherals of multiple versions can be deployed as a single snap package. The package contains metadata, specifying which firmware file is intended for which class of peripherals or which individual peripherals.

The packaging and deployment is a highly automated process – which will be described in detail in the following chapter, not because a user needs to know the details, but because it’s valuable knowledge to understand how the system works.

We’ll also explain, how to package firmware as a snap package and how to validate, if the firmware was properly deployed.

3.6.2. Prerequisites

  • Linux (Debian/Ubuntu based)

  • firmware files to be deployed

  • m2cp developer tools for Linux must be installed

3.6.3. Firmware Files

Our firmware is build based on SUIT (Software Updates for Internet of Things). The process for generating the firmware files is out of the scope of this document. We’ll assume to have a set of valid firmware files.

Example:

hwr-0_fwt-22_fwr-202402300_fws-0.bin
hwr-0_fwt-22_fwr-202402300_fws-1.bin
hwr-0_fwt-22_fwr-202402300.mani
hwr-0_fwt-22_fwr-202402301_fws-0.bin
hwr-0_fwt-22_fwr-202402301_fws-1.bin
hwr-0_fwt-22_fwr-202402301.mani
hwr-0_fwt-22_fwr-202402302_fws-0.bin
hwr-0_fwt-22_fwr-202402302_fws-1.bin
hwr-0_fwt-22_fwr-202402302.mani

Each firmware consists of three files:

  • a .mani file containing the manifest

  • a _fws-0.bin and a _fws-1.bin file containing the firmware payload for slots 0 and 1 of the peripheral

The filenames encode, which class of peripherals the firmware is intended for:

hwr-<HARDWARE_REVISION>_fwt-<FIRMWARE_TYPE>_fwr-<FIRMWARE_VERSION>_fws-0.bin
hwr-<HARDWARE_REVISION>_fwt-<FIRMWARE_TYPE>_fwr-<FIRMWARE_VERSION>_fws-1.bin
hwr-<HARDWARE_REVISION>_fwt-<FIRMWARE_TYPE>_fwr-<FIRMWARE_VERSION>.mani

It’s crucial, that the filenames are correct, as they are parsed by the packaging tool.

3.6.4. Packaging Tool

To package the firmware files, we use the m2cp-coap-manager tool, which is contained in the developers tools for Linux. This CLI tool scans a given path for firmware files and packages them into a snap package with a custom name and version number.

The package will contain the firmware files, additional metadata derived from the firmware file names and a deployment tool, which will push the firmware – not directly to the peripheral! – but to the m2cp-coap server on the M2CP device. This server maintains an archive of all available firmware files and offers them to the peripherals via a CoAP endpoint.

Note

UNDER DEVELOPMENT: In a future version you’ll be able to create an optional policy file for each firmware set. The policy file is a simple JSON file defining a default policy (allow/deny) and optionally providing a list of serial numbers of the sensors that are excepted from the default rule. Therefor you can either allow a firmware for all sensors except a specific list, or deny a firmware for all sensors except a specific list. By default, the policy is set to allow-all.

CURRENTLY: The policy is always set to allow-all. That means: when you deploy firmware to a device, all peripherals with matching hwr and ftw (= technically compatible) will be able to pull the updates. Please notify the m2cp-team, when you have a use-case requiring the more precise policies, which are planned.

Let’s assume that our firmware files are in the directory ./firmware and we want to package them into a snap package called “my-firmware” with version “1.0.0”, to be exported to directory ./snap:

m2cp-coap-manager firmware-snap -i ./firmware -o ./snap -n "my-firmware" -v "1.0.0"

The tool will create the file ./snap/my-firmware_1.0.0_arm64.snap, which can be deployed to the appstore.

Please read the output of m2cp-coap-manager carefully to verify, that it found and processed your firmware files correctly. The output should list all files that were added to the resulting snap.

To verify the contents of the produced snap file, you can use the Linux tool unsquashfs to extract and view the contents.

$ unsquashfs <snap-filename>

If you don’t have unsquashfs installed, use:

sudo apt-get update && sudo apt-get install squashfs-tools

3.6.5. Deployment

As usual, the app must now be assigned to a Deployment Group of devices to be deployed. It will then be installed on all the devices of the Deployment Group. Once installed, the app will – after each boot - contact the m2cp-coap server on the M2CP device and offer the firmware files contained in the package. It sends a list of its available files together with their hash sums and waits for the CoAP server to request files that are not yet known to the server. Those files are transferred from the app to the server. The app then shuts down until the next boot – while the server notifies peripherals of the new firmware files. The peripherals can then request the firmware files from the server.

To learn more about deployment using the app store, please refer to Deployment Groups.

3.6.6. Validation

Validation of the firmware deployment is currently (as of 2024-05-30) still a manual process without a comfortable UI.

In the future, we plan to visualize the currently installed firmware versions of all peripherals in the appstore.

Until then, there’s multiple manual ways to check, which firmware is currently installed on a peripheral. You should choose the method which is most convenient for you.

  • Use the /whoami/1 endpoint of the peripheral to get the firmware version. This requires you to have direct access to the internal network of the M2CP-Device and its peripherals.

  • Review the SIGNAL messages emitted by m2cp-coap. After successfully installing a firmware, the app will emit a SIGNAL message with the firmware version. This can be seen in the appstore logs.

  • Review the logs of the m2cp-coap server. The server logs all requests and responses. You can see, which firmware files were requested by which peripheral.

  • Review the DATA messages with device information emitted by each peripheral at boot.

# CoAP and Networking

Edge Devices and Real Time Devices communicate via CoAP. This chapter gives some insights on the IP-Addresses and Endpoints used. 

As this communication is highly project specific by nature, we can only give a brief overview of basic functionality. Individual 
projects extend or diverge from these details.

## LAN Addresses

Examples for typical fixed addresses in a M2CP setup:

| Node                | Address            | Comment                     |
|---------------------|--------------------|-----------------------------|
| PMIC                | fe80::df7:2023:1:1 | Power Management            |
| M2CP SoM            | fe80::df7:2023:1:2 | Linux System                |
| Power Board         | fe80::df7:2023:1:3 | Power Board                 |
| Communication Board | fe80::df7:2023:1:4 | Modem                       |
| Sensor Board        | fe80::df7:2023:1:5 |                             |

Depending on the use case, additional modules might exist or some modules might be missing.

## Contacting Modules

To talk to CoAP endpoints, you need to be in the same LAN as the CoAP nodes. This can be achieved by e.g.:

- Using Reverse-SSH to shell into a M2CP-OS device and running a CoAP client from there
- Directly connecting to the LAN using a cable connection with the switch

Once connected, any CoAP client can be used for calling the available endpoints. We'll use `coap-client` in the
following examples.

Example CoAP call:

```bash
$ coap-client -m GET 'coap://[fe80::df7:2023:1:1%eth1]/whoami/1'
{"sn":1234,"board":"mlpa_control","app":"mlpa_control_pmic","app_ver":"0","app_rev":0}
```

## Common CoAP endpoints

Here's a list of some of the most common and useful CoAP endpoints. For full specifications of endpoints, see [Tech CoAP — Endpoints](Tech_CoAP.md#endpoints).

### /whoami/1

Returns a self-description of the CoAP node. Every node in the M2CP system is expected to implement this endpoint — see [CoAP spec](Tech_CoAP.md#get-whoami-1-node-self-description) for the full response format.

Example:

```bash
$ coap-client -m GET 'coap://[fe80::df7:2023:1:1%eth1]/whoami/1'
{"sn":1234,"board":"mlpa_control","app":"mlpa_control_pmic","app_ver":"0","app_rev":0}
```

With `POST`, the same endpoint is used during provisioning to write the [Hardware Serial Number](Glossary.md#hardware-serial-number) of an Edge Device (write-once) — see [CoAP spec](Tech_CoAP.md#post-whoami-1-serial-number-provisioning) for encoding details.

### /uptime/1

Returns the number of seconds the node has been running as a string-encoded integer — see [CoAP spec](Tech_CoAP.md#get-uptime-1).


## Power Management
Power management is optional and requires a dedicated power management
MCU. The aim is to reduce power consumption by keeping the Linux
system in the power-off state as much as possible. At the time the
Linux system is required, the power management unit (PMU, which can be
any peripheral MCU) will start it up. The PMU will notify about the
granted uptime and it will cut the power, once the time is up.

### m2cp-coap's part in power management

The software responsible for managing uptime and initiating the Linux system shutdown in time is _m2cp-coap_. It reacts to power notifications from the PMU via [`POST /notify/poweroff/1`](Tech_CoAP.md#post-notify-poweroff-1) and allows applications to request uptime via [`PUT /request_uptime/1`](Tech_CoAP.md#put-request_uptime-1). The PMU can also command an immediate shutdown via [`POST /shutdown/1`](Tech_CoAP.md#post-shutdown-1). See the [CoAP endpoint specs](Tech_CoAP.md#power-management-endpoints) for the full protocol definition.

_m2cp-coap_ is dormant until a PMU introduces itself by sending the first `/notify/poweroff/1` message, which also registers the PMU's address. The received address is logged:

```console
$ sudo m2cp logs -f m2cp-coap
...setting power-board address to [...]
```

The PMU sends `/notify/poweroff/1` periodically (typically every 10 seconds) with the remaining uptime in seconds. On each notification _m2cp-coap_ compares the incoming `seconds` value against the highest uptime currently requested by any application or by _m2cp-coap_ itself, plus the expected shutdown duration. If the incoming budget is smaller than that sum, _m2cp-coap_ requests more uptime from the PMU. If the PMU does not grant the requested amount and the budget drops below the shutdown duration threshold, _m2cp-coap_ initiates a system shutdown. The current shutdown duration is 50 seconds — applications must not depend on this exact value.

The minimum system uptime (default 360 s) is configurable and persisted in `$SNAP_COMMON/power-manager.yaml`:

```console
$ cat /var/snap/m2cp-coap/common/power-manager.yaml
uptime-minimum: 360
```

For illustration, injecting a notification of 60 seconds of uptime manually:

```console
$ coap-client -m POST "coap://[fe80::df7:2023:1:2%eth0]/notify/poweroff/1?seconds=60"
```

Here `fe80::df7:2023:1:2` is the link-local address of the Linux system (M2CP SoM) and `eth0` is the network interface used.


### App's uptime requests

Apps request uptime from _m2cp-coap_ via [`PUT /request_uptime/1`](Tech_CoAP.md#put-request_uptime-1), providing the `app` name and `seconds` as query parameters (max 1000 s). See the [CoAP endpoint spec](Tech_CoAP.md#put-request_uptime-1) for details.

_m2cp-coap_ maintains a list of uptime requests per application. On each `/notify/poweroff/1` notification it compares the remaining budget against the highest outstanding request plus the shutdown duration, and asks the PMU for more time if needed.

For convenience, the SDK provides a function for this — see [Requesting App Runtime](Development_Edge.md#requesting-application-runtime).

Example:

```console
$ coap-client -m PUT "coap://[fe80::df7:2023:1:2%eth0]/request_uptime/1?app=example&seconds=300"
```


### getUptimeRequests RPC

`m2cp-coap` provides the `getUptimeRequests` RPC, which will answer
with a list of who requested which amount of uptime:

```
$ m2cp device node rpc -c getUptimeRequests rpc.m2cp-coap.49eb343c-31f0-5b8d-98a9-b53c21aadac1 --json |\
  jq '.output.response.responses[0].results[0].value | fromjson'
{
  "m2cp-gateway_ConfigRefresher": {
    "RequireUptimeUntil": "2024-11-07T14:15:42.383550671Z",
    "RequireUptimeSeconds": -50.609242449999996
  },
  "m2cp-gateway_DeviceKeyHandler": {
    "RequireUptimeUntil": "2024-11-07T14:15:42.386935745Z",
    "RequireUptimeSeconds": -50.605856502
  },
  "m2cp-gateway_SnapRefresher": {
    "RequireUptimeUntil": "2024-11-07T14:15:45.393435002Z",
    "RequireUptimeSeconds": -47.599355371
  },
  "m2cp-gateway_UserRefresher": {
    "RequireUptimeUntil": "2024-11-07T14:15:45.390217057Z",
    "RequireUptimeSeconds": -47.602574565
  },
  "uptime-mgr": {
    "RequireUptimeUntil": "2024-11-07T13:47:08.650916832Z",
    "RequireUptimeSeconds": 281.359757326
  }
}
```

A negative amount of `RequireUptimeSeconds` means "the requested
amount has has expired" since that absolute amount of seconds. This
way it is possible to trace that some App requested uptime in
the past. `uptime-mgr` is the label for the amount of minimum uptime
that is requested by `m2cp-coap` itself.


### dev-m2cpctl integration

Also the `dev-m2cpctl` app contains the `m2cpctl` binary that can be
used to request or set the uptime on a Device in a convenient way:

```
$ sudo dev-m2cpctl.m2cpctl uptime list
uptimerequests:
    m2cp-cli_: 987
    uptime-mgr: 159

$ sudo dev-m2cpctl.m2cpctl uptime request 1000
```

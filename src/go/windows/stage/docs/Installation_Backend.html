3. Cloud Installation

This section adresses users meant to set up the Backend Services and work directly with the systems APIs. It covers how to install the App Store Service. Additionally, it explains the data points that are being received and discusses the purpose and usage of the two main interfaces: the Event API and the GraphQL API.

3.1. Installing Backend Services

There are two ways to install the backend services of L-IoT, via bicep or via terraform. The terraform installation is the preferred way. The bicep installation is not feature complete and will be deprecated in the future.

3.1.1. Azure

Requirements

  • Resource Group in the determined subscription for each environment (e.g. dev, prod)

    • ensure at least read access for one technical employee of ML!PA

  • Service Connection to the Resource Group(s) in Azure DevOps

    • when terraform is used, the service connection needs to have contributor permissions on subscription level

    • service connection needs to have the ‘Microsoft.Authorization/roleAssignments/write’ & Microsoft.Authorization/roleDefinitions/write permission, can be aquired through the role ´Role Based Access Control Administrator´

      • One way to achieve this is to create a custom role with the required permissions and assign it to the service connection. A script can be found in the ml-pa project.

  • SQL Server Admin Group, in the MS Entra, with at least one technical employee of ML!PA as a member

    • Name, tenantId and the Sid (object Id) of the group are required to obtain

  • “Appstore Observer” Group, for all people who should have read access to the appstore

  • “Appstore Emergency” Group, for all people who should have emergency (read + write + actions) access to the appstore

  • DevOps Repository for the infrastructure code

    • It is not required to be a separate repository, but it is recommended, it can also be a subfolder in an existing repository

    • Permissions to create a new pipeline in the project

  • Access to the container registry, where the docker images of the services are stored

    • for instructions see section Container Registry

Terraform

The terraform code provides more options of deployment and is the preferred way to deploy the infrastructure. The terraform code is located in the terraform folder of the ml-pa project. A description of the parameters and modules, can be found in the README.md file in the terraform folder.

Deployment Requirements

Next to the already mentioned requirements, the following requirements are needed to deploy the infrastructure via terraform:

  • A storage account to store the terraform state file. It is recommended to place that storage account in a separate resource group.

    • The service connection that deploys the infrastructure needs to have the role Storage Blob Data Contributor on that storage account.

  • A secrets file in the library from devops, the secrets are described in the readme of the repository.

    • If secrets are updated, then the the secrets file also need to be updated in the devops library.

    • Due to the loss of sensitive information, the secrets file should not be stored in the repository.

  • An Azure Devops environment with an approval gate for the deployment needs to be created.

  • A .tfbackend file in the terraform folder, which contains the information about the storage account and the container where the terraform state file is stored. An example file can be found in the terraform folder of the ml-pa project.

Developer Requirements

When using terraform and the automatic deployment it is required to format the terraform code before pushing it to the repository. This can be done with terraform fmt --recursive in the terraform folder. The pipeline will fail if the code is not formatted.

Steps for a new project - Terraform

  1. Copy the files from the terraform folder of the ml-pa project to the new customer project.

  2. Create a new tfvars file in the terraform directory, based on the example file called dev.tfvars.

  3. Create a new secretes file in the terraform directory

    • The secrets.tfvars is not tracked in git, so it needs to be created manually. The secrets are described in the readme of the repository. Or the section constraints on secrets below. An example secrets file can be found in the terraform folder of the ml-pa project.

  4. Create a new tfbackend file in the terraform directory, based on the example file called $environment-config.azurerm.tfbackend. Where environment denotes the environment the infrastructure is deployed to, e.g. dev, prod.

    1. Update the storage account name, container name and key to match the previously created storage account.

  5. Copy the pipeline file from the ml-pa project to the new project.

    1. Replace the following variables with the new values:

      • serviceConnection

      • projectAbbreviation

      • environment

    2. If required replace the values of the following variables:

      • projectAbbreviation

      • varsFile

      • secretsVarsFile

      • terraformDirectory

    3. Adjust the agent pool.

    4. Adjust the pipeline trigger.

    5. (Optional) Adjust the pipeline name.

  6. Update the Subscription and TenantId in the local-provider.tf file to match your deployment destination.

  7. Register the pipeline in Azure DevOps.

Steps for existing projects that are not managed by terraform

After Deployment Steps - Terraform

In case a MS SQL Server is used, the same after deployment steps as in bicep are required.

Bicep

Steps - Bicep

If a new project for the appstore has been acquired, the following steps are required to deploy the resources:

  1. Copy the files from the bicep folder of the ml-pa project to the new customer project.

  2. Create a new parameters file for the new project.

    1. Use the internal.parameters.json as a template

    2. Replace the 3 letter abbreviation in the parameters file with the new abbreviation. E.g. int -> mlp

    3. Replace the information about the sql admin.

      • login is the name of the group in the MS Entra

      • tenantId is the tenantId of the group in the MS Entra

      • sid is the objectId of the group in the MS Entra

    4. Update the user groups (admin and emergency) with the corresponding object Id.

    5. Rename the parameters file to the new project name. E.g. internal.parameters.js on -> mlpa.parameters.json

  3. Copy the pipeline file from the ml-pa project to the new project.

    1. Replace the following variables with the new values:

      • projectName

      • resourceGroupName

      • serviceConnection

      • subscriptionId

    2. Optionally change the following variables:

      • location (then the short location in the parameters file has to be changed as well)

      • pathToBicepFiles

    3. Change the agent pool.

    4. (Optional) Create a second stage for prod

    5. Register Pipeline in Azure DevOps

    6. Save pipeline secrets, which is every secure parameter.

      • Secrets can be set, once the pipeline is registered

      1. Go to the freshly registered pipeline

      2. click on edit

      3. click on variables

      4. check the box “Keep this value secret”

    7. (Optional) Change trigger

  4. Execute the pipeline in Azure DevOps. Or create a commit.

After Deployment Steps - Bicep

  1. Connect to the SQL Server and add the managed identities for the appstore, asset and user database. The identity name is the name of the resource, e.g. “app-as3-int-appstore-svc-dev-euw”

    CREATE USER [<identity-name>] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [<identity-name>];
ALTER ROLE db_datawriter ADD MEMBER [<identity-name>];
ALTER ROLE db_ddladmin ADD MEMBER [<identity-name>];
GO

  2. Reconnect to the SQL Server and execute the following command for the appstore and user database to enable read and emergency access

    CREATE USER "Appstore Observer" FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER "Appstore Observer";

    and

    CREATE USER "Appstore Emergency" FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER "Appstore Emergency";
ALTER ROLE db_datawriter ADD MEMBER "Appstore Emergency";

  3. Copy the web hook URLs of the app services and azure functions into the variable group Appstore Container Web Hooks

    1. You can find them in the Azure Portal in the respective resource: Deployment -> Deployment Center -> Webhook URL

  4. Copy the URL of the Update container function into the variable group Appstore Container Web Hooks

3.2. Constraints on secrets

This section describes the constraints on the secrets and configuration of the services, if you are deploying the services in a new envrionment. Specific secret values will not be exposed in this document, and shouldn’t be exposed anywhere else. Some of the secrets and parameters need to be manually determined ahead of deployment time. In the following sections, we will discuss the constraints on the secrets and configuration of the services. An overview of the secret flow can be seen in the respective mermaid diagram. (Diagram not available in this repository.)

3.2.1. Secrets

The values of these secrets contain sensitive information and should be kept confidential. One option for deployment is the use of a secret management system, such as HashiCorp Vault, Azure Key Vault, or AWS Secrets Manager.

Secrets for firmware update process

As an interim solution, the SUIT manifest signing keys for the firmware update process must be generated manually and then stored in the Key Vault.

  1. Generate the Ed25519 key pair

openssl genpkey -algorithm Ed25519 -out private_key.pem
openssl pkey -in private_key.pem -pubout -out public_key.pem

The generated private key must begin with -----BEGIN PRIVATE KEY-----.

  1. Store the keys in the Key Vault

For the interim setup, upload the very same key pair twice under the following names (two naming schemes referencing the same underlying keys):

  • suit-manifest-production-signing-private-key-<YYYYMMDD-HHMMSS>

  • suit-manifest-production-signing-public-key-<YYYYMMDD-HHMMSS>

  • suit-manifest-signing-production-private-key

  • suit-manifest-signing-production-public-key

Timestamp format

  • The timestamp is the key creation date and time in the format YYYYMMDD-HHMMSS (24-hour clock)

  • Example: Created on 27 June 2025 at 14:02:12 → 20250627-140212.

  • Example secret names:

    • suit-manifest-production-signing-private-key-20250627-140212

    • suit-manifest-production-signing-public-key-20250627-140212

UserServicePublicSigningKey

The services use an internal JWT token for authorization. To sign the JWT token, the user service use an RSA key pair with 2048 bits. This secret is the public key part of the key pair. Only the base64 part of the key is needed, so no header or footer.

UserServiceSigningPrivateKey

The services use an internal JWT token for authorization. To sign the JWT token, the user service use an RSA key pair with 2048 bits. This secret is the private key part of the key pair. Only the base64 part of the key is needed, so no header or footer.

customerOpenIdAudienceSecret

The customer can use an OpenID Identity Provider for authentication. This secret is the Audience contained in the JWT token, used for authentication with the customer OpenID Identity Provider.

customerOpenIdMetadataAddressSecret

The customer can use an OpenID Identity Provider for authentication. This secret is the Address of the metadata endpoint of the customer OpenID Identity Provider.

customerOpenIdValidIssuerSecret

The customer can use an OpenID Identity Provider for authentication. This secret is the Issuer of the JWT token, used for authentication with the customer OpenID Identity Provider.

mLPAAzureADAudience

ML!PA uses MS Entra ID for authentication. To enable the ML!PA developers to use the ecosystem, the services need to authenticate with the ML!PA MS Entra ID. This secret is the audience contained in the JWT token.

mLPAAzureADTenantId

The tenant Id of the MS Entra ID of ML!PA used by the ML!PA developers to authenticate. It is in a UUID format.

reverseSshSvcApiKey

The relay ssh service uses an API key for authentication. This secret is the API key used for authentication with the relay ssh service. Randomly generated long enough stirng secure. Aim for at least 50 chars, the longer the better. Needs to be identical to relaySshLocalDockerApiKeySecret, relaySshLocalDockerApiKeySecret, api-key-snapstore3-dev, api-key-snapstore3-local-docker.

relaySshLocalDockerApiKeySecret

The relay ssh service uses an API key for authentication. This secret is the API key used for authentication with the relay ssh service. Needs to be equal to reverseSshSvcApiKey. Randomly generated long enough stirng secure. Aim for at least 50 chars, the longer the better.

relaySshDockerRegistryPasswordSecret

Password for the docker registry, where the relay ssh docker image is stored.

relaySshDockerRegistryUsernameSecret

Username for the docker registry, where the relay ssh docker image is stored.

api-key-snapstore3-dev

Needs to be equal to reverseSshSvcApiKey. Random long enough to be secure strings. Aim for at least 50 chars. Needs to be identical to relaySshLocalDockerApiKeySecret.

api-key-snapstore3-local-docker

Random long enough to be secure strings. Aim for at least 50 chars.

DOCKER_REGISTRY_SERVER_PASSWORD

Password for the docker registry, where the service docker image is stored.

DOCKER_REGISTRY_SERVER_USERNAME

Username for the docker registry, where the service docker image is stored.

3.4. Event API

While the GraphQL API lets you query the current state of the system, the Event API lets you subscribe to changes (events).

Whenever the state of an entities is changed (creation, modification, deletion), an event is emitted. Events are thin, meaning they only contain the minimum information necessary to identify the entity and the change. If you need more information about the new state of the entity after the change, you can use the GraphQL API or the REST API to query it.

The Event API is designed to:

  • Provide instant updates when important events occur (e.g., when a new Device is added)

  • Eliminate the need for constant polling

  • Enable event-driven workflows, allowing services to listen for updates instead of making direct API calls

Messages being received through the Event API are structured as follows:

{
  "event": "205e8259-b7df-4961-86dd-d46e03f00279",
  "time": "2024-06-01T00:07:35.555539Z",
  "entity": "user",
  "entityId": "b5d1c4fa-9876-4e3a-bf07-d4a2f3c92e4b",
  "action": "created"
}

  • event is a unique identifier for the event

  • time is the timestamp of the event in ISO 8601 UTC

  • entity is the type of entity that was changed, possible values are …

  • entityId is the unique identifier of the entity that was changed, you can use it to query the new state of the entity using the GraphQL API or the REST API

  • action is the type of change that occurred, possible values are created, updated, deleted

3.4.2. Receiving Data Points

Data points from edge Devices are transmitted to the backend, where the ingestion function unpacks them and publishes them on the Event API. While events for most entities are published as thin events (i.e. only the entity ID and the action), data points are published as thick events. Thick events contain the full data point, including all data fields, in a human-readable format. This allows you to process the data point directly without having to query the GraphQL API for more information.

{
  "event": "3db2d9fe-2328-45b6-934b-a325aa808151",
  "time": "2024-06-01T00:07:35.555539Z",
  "entity": "dataMessage",
  "entityId": "0907ffab-6d9f-5574-b4c0-a56bbfa3de75",
  "action": "created",
  "data": {
    "device": "0907ffab-6d9f-5574-b4c0-a56bbfa3de75",
    "topic": "sensor.JiMAAA.oid.104.protobuf",
    "origin": "sensor.JiMAAA.oid.104.protobuf.m2cp-coap.0907ffab-6d9f-5574-b4c0-a56bbfa3de75",
    "format": "coap_data_protobuf",
    "fields": {
      "time": { "value": "2024-06-01T00:08:48.822539Z", "type": "timestamp" },
      "foo": { "value": "JiMAAA", "type": "string" },
      "bar": { "value": "CJDN6bIGEAAYACAAKAAwADgAQLEJSAA=", "type": "binary" }
    }
  }
}

  • event is a unique identifier for the event

  • time is the timestamp of when the data point was received by the cloud backend

  • entity is dataMessage for data points

  • entityId is the id of the DATA message which contained the data point (a DATA message can contain multiple data points!)

  • action is created for data points

  • data contains the full data point…

  • data.device is the Device ID of the Device that sent the data point

  • data.topic is the topic of the data point as set by the app that sent the data point

  • data.origin is the full m2cp-address of the sender of the data point (node name + App Name + Device ID)

  • data.format is a free text field set by the app that sent the data point to identify the format of the data point

  • data.fields contains the actual data fields of the data point. Each field has a name, a value and a type.

  • data.fields.time is the timestamp of the data point (that maps to the T field in the table section of the data message)

  • data.fields.<name> is additional fields of data

Available data types are defined in the Message Format Specification.

3.5. GraphQL API

General data access within L-IoT is structured by seperation of concerns. The Event API handles real-time updates, ensuring timely notifications, while the GraphQL API provides deep, structured data retrieval. To structure it this way balances real-time event-driven communication with flexible, query-based data access, improving maintainablity and efficiency for users.

The GraphQL API is designed to:

  • Allow clients to request exactly the data they need, reducing unnecessary data transfer

  • Provide a single entry point for accessing all system information

  • Enable efficient data aggregation, allowing related information to be retrieved in a single query

3.6. REST API

The REST API is another way to access all information in a flexible and query-based way similar to the GraphQL API. The complete REST API documentation is organized into separate HTML files based on the respective services. It is divided into three sections: the REST API documentation for the User Service, the Asset Service, and the App Store Service.

The API follows a structured approach using YARP for request routing from the gateway to underlying services.

3.6.1. Authentication & Authorization

  • The authentication and authorization mechanism is shared with our GraphQL endpoints.

  • All endpoints require authentication unless explicitly mentioned.

3.6.2. Swagger API Documentation

The swagger documentation is also accessible through the gateway:

https://[gateway-service]/swagger

3.6.3. Requests

Requests to the API gateway are forwarded to backend services based on predefined rules.

https://[gateway-service]/api/v{version}/{entity}?param1=value1&param2=value2
https://[gateway-service]/api/v{version}/{entity}/{id}

  • [gateway-service]: The same endpoint used for GraphQL but without the /graphql postfix

  • {version}: API version (e.g., v1)

  • {entity}: Plural form of entity names

Pagination

The API supports pagination using the following optional query parameters:

Parameter

Type

Description

pageSize

int?

The number of items per page. If omitted, Items are returned based on the configured max page size.

pageNumber

The page number to retrieve (starting from 1).

includeTotalCount

If true, includes the total count of records only when pageNumber = 1. Default is false.

Sorting

The API supports sorting using the sort query parameter. Sorting can be applied to one or multiple fields in ascending (asc) or descending (desc) order.

?sort=<field1> <order>, <field2> <order>, ...

/api/v1/users?sort=email
/api/v1/users?sort=email desc
/api/v1/users?sort=firstName asc, lastName asc

Filtering

The API supports filtering using the filter query parameter. Filters can be applied to one or multiple fields with various operators. Grouping conditions using parentheses ( and ) is also supported.

  • Multiple filters can be combined using and / or.

  • Parentheses ( and ) can be used to group conditions.

Examples:

/api/v1/users?filter=email = "user@organization.com"
/api/v1/users?filter=email eq "user@organization.com"
/api/v1/users?filter=email neq "user@organization.com"
/api/v1/users?filter=displayname.contains("foo")
/api/v1/users?filter=displayname.contains("foo") or displayname.startswith("bar")
/api/v1/users?filter=(lastname = "foo" and firstName.startswith("bar")) or (lastname != "Jackson")
/api/v1/users?filter=(modifiedat >= "2025-01-01" || createdat >= "2025-01-01")

6. CoAP

This section provides reference definitions for the CoAP interface of the L.IoT system. It covers the available endpoints and the data formats used in CoAP messages.

  • Endpoints Definitions of the CoAP endpoints exposed by nodes in the L.IoT system, including /din/1/{sensorId} and /din/2/{osSerial} for RTD data ingestion, and /cmd/1/{sensorId} for RTD command batch exchange.

  • Formats Definitions of the data formats used in CoAP messages, including RTD Details, CommandBatch, and ResponseBatch.

6.1. Endpoints

The following subsections define each CoAP endpoint used in the L.IoT system.

6.1.1. /din/1/{sensorId}

Purpose: A Real Time Device sends one or more data messages to the Edge Device, identified by its hardware serial number.

Property

Value

Direction

RTD → ED

Method

POST

Path Params

sensorId: base64-encoded hardware serial of the RTD

Request Body

Binary: one or more framed protobuf messages (see below)

Response

—

m2cp-coap parses each message, dispatches it to a registered OID parser if one exists, and forwards the result into the messaging system. If no parser is registered for a given OID, the raw protobuf is forwarded as unparsed data. Messages with OID 18 are handled specially as log/signal messages. Data is tagged with the sensorId as the device identifier (DIN1 standard).

Resulting message topics

Messages are published on the message-hub using the address format <feature>.<app>.<device>.

For /din/1, <device> is the OS Serial Number of the Edge Device serial. The feature and app segments depend on whether the OID is known to m2cp-coap:

Scenario

Topic (feature part)

App segment

Notes

OID unknown to m2cp-coap

sensor.<sensorId>.oid.<oid>.protobuf

m2cp-coap

Raw protobuf forwarded as-is

OID unknown, custom parser present

sensor.<sensorId>.oid.<oid>.parsed

<parser-app>

Parser emits second message after consuming the protobuf message

OID known to m2cp-coap

sensor.<sensorId>.oid.<oid>.parsed

m2cp-coap

Parsed inline; no intermediate protobuf message

sensorId is the base64-encoded hardware serial of the RTD, as provided in the URL path parameter.

Example (OID 1, sensorId = ew, ED serial = b9961153-efa6-520b-b21f-905d34d775e3):

sensor.ew.oid.1.protobuf.m2cp-coap.b9961153-efa6-520b-b21f-905d34d775e3
sensor.ew.oid.1.parsed.demo-oid-parsers.b9961153-efa6-520b-b21f-905d34d775e3

See /din/2/{osSerial} for the alternative that uses the OS Serial Number of the RTD instead.

See also: Messaging — Data Points to Data Visualization, DATA Flow Debugging — m2cp-coap, Simulating OID Data Flow

6.1.2. /din/2/{osSerial}

Purpose: A Real Time Device sends one or more data messages to the Edge Device, identified by its OS Serial Number.

Property

Value

Direction

RTD → ED

Method

POST

Path Params

osSerial: URL-safe base64 (no padding) of the RTD’s OS Serial Number (UUIDv5)

Request Body

Binary: one or more framed protobuf messages (see below)

Response

—

Behaviour is similar to /din/1 except that the device is identified by its OS Serial Number rather than its hardware serial.

The advantage over /din/1 is that using the RTDs OS Serial Number allows to discover the messages of one specific RTD even if it is moving between different Edge Devices. With din/1, one has to search through different EDs messages, which is far more complex and time consuming.

The OS Serial Number for an RTD is a UUIDv5 derived from hardware properties — see Tech Lifecycle RTD — Known Peers for the derivation details.

Resulting message topics

Messages are published on the message-hub using the address format <feature>.<app>.<device>.

In comparison to /din/1, the RTDs OS Serial Number is used directly in the <device> segment instead of the EDs OS Serial Number. Thus the hardware serial (sensorId) in the topic can be omitted.

Scenario

Topic (feature part)

App segment

Notes

OID unknown to m2cp-coap

oid.<oid>.protobuf

m2cp-coap

Raw protobuf forwarded as-is

OID unknown, custom parser present

oid.<oid>.parsed

<parser-app>

Parser emits second message after consuming the protobuf message

OID known to m2cp-coap

oid.<oid>.parsed

m2cp-coap

Parsed inline; no intermediate protobuf message

The full address includes the OS serial as the <device> segment. Example (OID 1, OS serial = ab-cd-ef):

oid.1.protobuf.m2cp-coap.ab-cd-ef
oid.1.parsed.protobuf-parser.ab-cd-ef

See also: Messaging — Data Points to Data Visualization, DATA Flow Debugging — m2cp-coap, Simulating OID Data Flow

6.1.3. /whoami/2

Purpose: Supersedes whoami/1 on Real Time Devices. An Edge Device queries a Real Time Device for its current hardware and firmware details.

Property

Value

Direction

ED → RTD

Method

GET

Request Body

—

Response

RTD Details

This endpoint is called during the Peers Discovery phase, both via IPv6 multicast (GET coap://[ff02::1]/whoami/2) and by individual unicast requests to each known peer. Implementing this endpoint is recommended for better discovery, but is not required — Real Time Devices that do not implement a CoAP server can instead announce themselves using /hello/2.

See also: Peers Discovery

Method

Direction

Purpose

Any client → Any node

See also: Legacy Real Time Devices

POST

Purpose: Writes the Hardware Serial Number of an Edge Device. The operation can be performed only once — the device stores the assigned serial and rejects subsequent writes.

Property

Value

Direction

Provisioning tool → Edge Device

Method

POST

Host

Edge Device only (not implemented by RTDs)

Request Body

Hardware serial number: 16-bit unsigned integer, little-endian, base64-encoded without padding

Response

—

The serial is a 16-bit unsigned integer encoded in little-endian byte order and base64 without padding.

Example — encoding serial 8667 to 2yE:

import struct, base64
hardware_serial = 8667
base64.b64encode(struct.pack('<H', hardware_serial)).decode().rstrip('=')
# '2yE'

Decoding back to integer:

import struct, base64
encoded_serial = '2yE'
struct.unpack('<H', base64.b64decode(encoded_serial + '=' * (-len(encoded_serial) % 4)))[0]
# 8667

6.1.8. /status/clients/1

Purpose: Returns the list of known CoAP clients (RTDs) that the Edge Device has seen.

Property

Value

Direction

Any client → Edge Device

Method

GET

Request Body

—

Response

JSON array of known clients

Each entry in the response array contains the client’s IP address and the timestamp it was last seen:

[
  {
    "Address": "fe80::1",
    "LastSeen": "20260407T143000Z"
  }
]

LastSeen is formatted as a compact ISO 8601 UTC string (YYYYMMDDTHHmmssZ), matching the format used by /realtime/1. An empty array is returned if no clients are known.

Purpose: Reports the internet connectivity status of the Edge Device by running a set of active probes.

Property

Value

Request Body

—

JSON object with one field per probe

Probe

}

6.1.10. /status/ping/1

Purpose: Pings an arbitrary address from the Edge Device, optionally via a specific network interface.

Property

Value

Direction

Any client → Edge Device

Method

GET

Query Params

interface={string}: network interface to use (optional); address={string}: target host or IP (required)

Request Body

—

Response

Plain text: ok or an error string

The ping is issued with a 15-second timeout (-W15). If interface is provided, the ping is bound to that interface (-I<interface>).

Example:

$ coap-client -m GET "coap://[fe80::df7:2023:1:2%eth0]/status/ping/1?interface=eth0&address=8.8.8.8"
ok

6.1.21. /cmd/1/{sensorId}

Purpose: A Real Time Device reports the result of the previously executed command batch and requests the next one from the Edge Device.

Property

Value

Direction

RTD → ED

Method

POST

Path Params

sensorId: base64-encoded hardware serial of the RTD

Request Body

ResponseBatch (CBOR)

Response

CommandBatch (CBOR, 2.05 Content), or 2.03 Valid if no next batch is available, or 4.12 Precondition Failed if the exit code does not satisfy the next batch’s constraint

The RTD sends the result of the last executed command batch as a CBOR-encoded ResponseBatch.

m2cp-coap processes the result and looks up the next command batch (sequence number = reported seq + 1) for the device. The next batch is returned only if:

  • A batch with the next sequence number exists for the device, and

  • The batch’s LastExitCodeConstraint is satisfied by the exit code of the last command in the reported result (or the constraint is unconstrained, i.e. -1).

If a fast-forward batch exists for the device at a higher sequence number, it takes precedence over the next entry.

On success the response body contains the CBOR-encoded CommandBatch.

6.2. Formats

The following data formats are used in CoAP message bodies.

6.2.1. RTD Details

RTD Details describe a Real Time Device’s current hardware and firmware state. They are exchanged via:

  • /hello/2: RTD announces itself to the ED

  • /suit/mani: RTD requests a firmware manifest from the ED

  • /whoami/2: ED receives RTD details from the RTD

Both JSON and CBOR encodings are supported.

JSON Format:

{
  "hw_serial": "12345",      // The Device Hardware Serial
  "hw_model": "PMIC 1.08",   // The Device Hardware Model
  "hw_vendor": "mlpa",       // The Device Hardware Vendor
  "mcu_id": "123abc",        // Optional: The MCU ID
  "dev_model": "pmic",       // The Device Model of the Real Time Device
  "app_name": "fw-pmic",     // The name of the App running on the Real Time Device
  "app_version": "3.2.1",    // The semver version of the App running on the Real Time Device
  "seq_no": 2001000,         // The sequence number of the current firmware installation
  "uptime": 12345,           // The uptime of the Real Time Device in seconds
  "keys": ["key1", "key2"]   // Array of base64 encoded public keys
}

CBOR Format:

DeviceInfo = {
  0: tstr,       ; hw_serial
  1: tstr,       ; hw_model
  2: tstr,       ; hw_vendor
  3: tstr,       ; dev_model
  4: tstr,       ; app_name
  5: tstr,       ; app_version
  6: uint,       ; seq_no
  7: uint,       ; uptime
  8: [+ bstr]    ; keys
  9: ? tstr      ; mcu_id (optional)
}

6.2.2. CommandBatch

A CommandBatch is a CBOR-encoded ordered list of commands for a Real Time Device to execute. It is returned by /cmd/1/{sensorId} on success.

CommandBatch = {
  "seq": uint,      ; sequence number of this batch
  "cmd": [+ Cmd],   ; ordered list of commands to execute
  "cfg": any        ; optional: configuration object
}

Cmd = { tstr => any }   ; command name => argument(s)

6.2.3. ResponseBatch

A ResponseBatch is a CBOR-encoded report of the execution results of a previously received CommandBatch. It is sent by a Real Time Device as the request body of /cmd/1/{sensorId}.

ResponseBatch = {
  "seq": uint,           ; sequence number of the batch that was executed
  "rsp": [+ ResponseRsp] ; per-command results (omitted if empty)
  "error": int           ; CBOR parsing error code, if the batch could not be parsed (omitted if 0)
}

ResponseRsp = { tstr => [output, exitCode] }
; output    = any    (stdout/stderr lines or similar)
; exitCode  = uint
